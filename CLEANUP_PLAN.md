# Plan: Migrate `*_dev/` → `src/` + `scripts/`, slice by slice

## Context

The repo currently has a stable layer (`src/`, `scripts/`) and an active-work layer (`src_dev/`, `scripts_dev/`). The stable layer is mostly empty: only `src/utils/` is actively used (LoRA arithmetic — battle-tested, 17+ import sites). `src/inference/` and `src/lora_pipeline_persona_shattering/` are orphaned abstract-base stubs. `scripts/` does not exist yet. All real code — 20 packages in `src_dev/`, 27 dirs in `scripts_dev/` — lives in the dev layer.

The paper (Sections 3–4 + heavy appendices) depends on ~21 figure scripts and a handful of eval/training pipelines. To make the research reproducible and to position the project for replication on other model families, we want a clean `src/` (reusable library code) and `scripts/` (curated, runnable end-to-end entrypoints) layer that is a strict superset of what the paper needs, with cleaner organisation and (some) consolidation of obvious duplication.

**Goals:**
- A reader with HF monorepo data can run `scripts/figures/<...>.py` and regenerate any paper figure.
- A reader with compute can run `scripts/training/<...>.py` → `scripts/evals/<...>.py` → `scripts/figures/<...>.py` end-to-end.
- `src/` is reusable infrastructure that extends cleanly to new model families and new traits.
- `*_dev/` keeps working as the active workspace; team members' existing imports do not break.

**Non-goals (for this plan):**
- Cleaning up the HF monorepo (separate effort, but the new `src/` must read the existing layout).
- Pruning `*_dev/` code (others still depend on it).
- Building a top-level orchestrator (`make reproduce-paper`). Individual scripts only.

---

## Migration principles

1. **Vertical slices, one paper section at a time.** Each slice is independently end-to-end runnable (training-optional, figures mandatory) before the next slice begins.
2. **Migrate, don't fork.** Copy from `*_dev/` into `src/`+`scripts/`, then refactor in place. Originals stay; team members keep their imports.
3. **Refactor opportunistically.** Consolidate near-duplicate scripts (>80% shared logic) into one parameterised version. Do not consolidate when scripts diverge meaningfully — and keep the `% Generated by:` LaTeX comments updated when names change.
4. **Smoke test + figure regeneration is enough for each slice's "done"**, with full end-to-end re-run flagged as a TODO. Full re-runs will happen when we replicate the research on other model families anyway.
5. **`src/utils/` stays; orphaned stubs in `src/` get deleted** when their replacement lands (interfaces are designed once we know how the implementations actually compose).
6. **Cost discipline.** Plumbing work (`--dry-run`, import checks, CLI smoke tests) on a cheaper model per `CLAUDE.md`.

## Layout

Top-level structure that we'll grow into:

```
src/
  utils/                       # already exists, keep as-is
  datasets/                    # canonical dataset loading/normalization (from src_dev/datasets)
  generation/                  # response generation against base+LoRA (from src_dev/inference)
  trait_amplification/         # rewrite/edit responses (from src_dev/lora_pipeline_persona_shattering/editing)
  training/                    # LoRA training (from src_dev/lora_pipeline_persona_shattering/training)
  evals/                       # trait/MMLU/judge sweeps (from src_dev/evals)
  persona_metrics/             # per-response trait scoring
  visualisations/              # PAPER_FIGURES_DIR, shared plotting helpers
  factor_analysis/             # unsupervised (later slice)
scripts/
  training/                    # one script per (training method × OCEAN±) where applicable
  evals/                       # trait_sweep, mmlu_sweep, judge_sweep entrypoints
  figures/                     # paper figure scripts, one per \includegraphics target
  unsupervised/                # FA pipeline orchestration
  combinations/                # LoRA arithmetic experiments
```

**Taxonomy notes:**
- `src_dev/inference/` → `src/generation/` (clearer to external readers; "inference" is overloaded with model-serving).
- `src_dev/lora_pipeline_persona_shattering/editing/` → `src/trait_amplification/` (says what it actually does — rewriting responses with a stronger LLM to amplify a trait).
- Other names (`training`, `evals`, `datasets`, `persona_metrics`) stay.
- Final taxonomy decisions are made *per slice* when we actually pick up that package. We commit to the names above as a working proposal, not a frozen contract.

**Naming cleanup during migration:** The HF monorepo paths and figure scripts use `vanton4_paired_dpo` / `vanton4` as method identifiers. Grep of `paper/{sections,appendices,main.tex}` confirms `vanton` appears **only** in `% Data:` / `% Generated by:` provenance comments and one `\todo` note — never in prose. `paired DPO` does appear in prose (as a method name). The figure filenames the paper includes already drop the `vanton4` prefix (e.g. `trait_sweep_<trait>_<dir>_paired_dpo.pdf`). Decision: in `src/` and `scripts/`, drop `vanton4` from script and module names (`paper_appendix_paired_dpo_*.py` → `appendix_paired_dpo_*.py`). Keep `vanton4_paired_dpo` in HF monorepo path strings — those artifacts are immutable. Maintain a mapping table in `src/training/README.md` when Slice 2 lands.

## Slice 1 (FIRST): Supervised — OCEAN trait/MMLU/judge scaling (figures-only)

**Paper coverage:** Section 3 main scaling figures + Appendix F (paired-DPO sweeps for all 10 OCEAN± adapters).

**Scope:**
- Migrate the 4 paired-DPO figure scripts + their direct `src_dev/` dependencies.
- *Do NOT* migrate training (`run_oct_pipeline.py`) yet — that's Slice 2.
- *Do NOT* consolidate the 3 `paper_appendix_paired_dpo_{trait,mmlu,judge}.py` files yet — discuss case-by-case (see below).

**Files to migrate (paths relative to repo root):**

Library code → `src/`:
- `src_dev/utils/hf_hub.py` → `src/utils/hf_hub.py` (already heavily depended on; promote it).
- `src_dev/evals/personality/analyze_results.py` → `src/evals/personality/analyze_results.py` (BIG_FIVE_COLORS, Wilson/BCa CI, logprob/MMLU/judge parsers — heavy reuse across all 4 figure scripts).
- `src_dev/visualisations/__init__.py` → `src/visualisations/__init__.py` (defines `PAPER_FIGURES_DIR`, the canonical figure output path).
- `src_dev/visualisations/ocean_spider.py` → `src/visualisations/ocean_spider.py` (used by the banner figure; small shared helper).

Scripts → `scripts/figures/`:
- `src_dev/visualisations/paper_main_o_plus_scaling.py` → `scripts/figures/main_ocean_scaling.py`
- `src_dev/visualisations/paper_appendix_paired_dpo_trait.py` → `scripts/figures/appendix_paired_dpo_trait.py`
- `src_dev/visualisations/paper_appendix_paired_dpo_mmlu.py` → `scripts/figures/appendix_paired_dpo_mmlu.py`
- `src_dev/visualisations/paper_appendix_paired_dpo_judge.py` → `scripts/figures/appendix_paired_dpo_judge.py`

For each migrated script:
- Update local imports to point to `src.*` instead of `src_dev.*`.
- Preserve the `PAPER_FIGURES = [...]` declaration.
- Update the corresponding `% Generated by:` comments in `paper/sections/*.tex` and `paper/figures/MANIFEST.md`.
- Add a module-level docstring explaining what HF monorepo data the script reads and what figure(s) it produces.

**Open question — consolidate the 3 paired-DPO appendix scripts?**
- They share: HF path resolution, OCEAN trait/direction iteration, output naming.
- They differ: metric extraction (trait logprobs vs MMLU breakdown vs judge JSONL), plot layout per metric, error-bar method (Wilson vs BCa).
- Recommendation: keep as 3 files. Extract shared helpers (HF path resolution, OCEAN iteration) into `src/evals/personality/paired_dpo_paths.py`. The metric-specific plotting stays per-script — that's where divergence is real.

**Critical-file shortlist (Slice 1):**
- New: `src/evals/personality/analyze_results.py`, `src/evals/personality/ocean_sweep_paths.py` (shared OCEAN iteration + HF path helpers — see Option A in Decisions log), `src/utils/hf_hub.py`, `src/visualisations/__init__.py`, `scripts/figures/{main_ocean_scaling,appendix_paired_dpo_*}.py`.
- Edits: `paper/figures/MANIFEST.md`, `paper/sections/{supervised,appendices/*}.tex` (just `% Generated by:` updates).
- Migration-status tracking: append entries to the "Migration status" section at the bottom of this file as files land in `src/`+`scripts/`. *No deletions* in `*_dev/` or in `src/` (orphan stubs `src/inference/`, `src/lora_pipeline_persona_shattering/` stay put — annotated as "superseded, kept for reference").

## Decisions log

Every non-obvious decision we make during the cleanup goes here. Each entry: **what we chose**, **what we considered**, **why**. Peers who disagree should add a new entry below pushing back on a specific decision rather than rewriting the plan top-to-bottom.

Format: `D<n> (YYYY-MM-DD): <one-line summary>`, then the body.

### D1 (2026-05-27): Migrate vertically by paper section, not horizontally by layer

**Chosen:** Each slice migrates one self-contained piece of the paper (Slice 1 = OCEAN scaling figures, Slice 2 = OCT training, etc.). Inside a slice we touch whatever `src/` + `scripts/` packages it needs.

**Considered & rejected:**
- *Horizontal layers* (all infra into `src/` first, then all scripts) — nothing end-to-end until very late; high risk of building abstractions that don't match real use.
- *Figures-first, backfill infra* — close to what we're doing for Slice 1 anyway, but the layer framing creates anti-incentives to migrate training/eval ever.

**Why:** Vertical slices give us "someone can reproduce X" milestones every slice. The paper-section framing also matches how peers think about the work.

---

### D2 (2026-05-27): Copy from `*_dev/`, don't move. No deletions anywhere

**Chosen:** Slice migrations *copy* files into `src/`+`scripts/` and update imports inside the copies. Originals in `src_dev/` and `scripts_dev/` stay untouched. Orphan stubs in `src/` (`src/inference/`, `src/lora_pipeline_persona_shattering/`) also stay — annotated as "superseded, kept for reference" once a replacement lands.

**Considered & rejected:**
- *Delete migrated `*_dev/` files* — would be a single source of truth, but breaks team members' in-flight imports unpredictably.
- *Decide per-slice* — adds cognitive overhead; the blanket "no deletions" rule is simpler.

**Why:** Team members are actively using `*_dev/` paths. The cost of duplicate code is much smaller than the cost of breaking someone's branch mid-experiment. We can prune in a separate, deliberate pass later (probably when migrating Slice 3 forces a `src_dev/evals/` rewrite anyway).

**Tracked in:** Migration status section at the bottom of this file.

### D3 (2026-05-27): Slice 1 keeps the 3 appendix paired-DPO scripts as 3 files, extracts shared helpers

**Chosen:** `scripts/figures/appendix_paired_dpo_{trait,mmlu,judge}.py` each stay as their own ~200-line entry point. Shared logic (OCEAN iteration, HF path resolution, inspect-log download) moves into `src/evals/personality/ocean_sweep_paths.py`.

**Considered & rejected:**
- *Option B — single parameterised `scripts/figures/appendix_paired_dpo.py --metric {trait,mmlu,judge}`* — saves ~200 more lines, single entry point, but mixes three divergent plot styles + two different CI methods (Wilson vs BCa) inside one file.
- *Option C — orchestrator + per-metric submodules* — most structured but premature; we don't yet know whether the trait/mmlu/judge triplet will keep being a stable shape.

**Why:** The paper's `% Generated by:` comments already list all three filenames on one line, so keeping 1:1 has no extra paper-edit cost. We'll see the same triplet pattern again in Slice 7 (activation capping). By then we'll have two data points on whether the shape is stable enough for Option B; revisit then.

### D4 (2026-05-27): `vanton4` drops from script names; stays in HF monorepo path strings

**Chosen:** Migrated scripts and modules drop the `vanton4` prefix. HF monorepo paths inside the scripts (e.g. `fine_tuning/llama-3.1-8b-it/ocean/.../vanton4_paired_dpo/evals/...`) keep `vanton4_paired_dpo` verbatim. A mapping table lands in `src/training/README.md` when Slice 2 migrates the training code.

**Considered & rejected:**
- *Leave names as-is* — `vanton4` is meaningless to external readers and one paper `\todo` literally complains about the name.
- *Rename in HF monorepo too* — would require regenerating every eval artifact; HF paths are immutable history.

**Why:** Confirmed by grep that `vanton4` appears in paper *only* in `% Data:` / `% Generated by:` comments and one `\todo` note, never in prose. Renaming script-level identifiers costs ~0; renaming HF paths costs everything.

### D5 (2026-05-27): Fig 1 banner deferred from Slice 1; its data dependencies migrate anyway

**Chosen:** `paper_main_fig1_banner.py` does *not* migrate in Slice 1. But the library code Slice 1 produces (`src/utils/hf_hub.py`, `src/evals/personality/ocean_sweep_paths.py`, `src/visualisations/__init__.py`) is enough for someone to pull the raw HF data underlying Fig 1.

**Considered & rejected:**
- *Migrate Fig 1 in Slice 1* — pulls in 3 sibling spider/delta scripts I haven't traced. Inflates Slice 1 scope significantly.

**Why:** User signaled "raw results > regenerated figures" for early slices. Fig 1 picks up cheaply later (it's only a banner, downstream of analyses that land in other slices).

---

### D6 (2026-05-27): Smoke-test + figure regeneration is "done" for each slice; full re-runs deferred

**Chosen:** A slice is considered landed when (a) its migrated scripts import cleanly, (b) figures regenerate from existing HF data and match the current PDFs visually, (c) `paper && make` still produces an unchanged PDF.

**Considered & rejected:**
- *Full end-to-end re-run per slice* (re-train, re-eval, re-figure) — most rigorous, but Slice 1 re-running costs ~$200 of compute and provides little new info.

**Why:** Full re-runs happen anyway when the project replicates the research on other model families. Doing it twice (once for migration validation, once for the actual replication study) is waste. Each slice carries a tracked "full-rerun TODO" instead.

---

### D7 (2026-05-27): `src/` taxonomy decided per-slice, not upfront

**Chosen:** The package layout proposed in this plan (`src/generation/`, `src/trait_amplification/`, etc.) is a working proposal, not a commitment. Final naming for each `src/<package>/` is decided when that slice actually migrates it. Anchor renames (chosen now): `inference` → `generation`, `editing` → `trait_amplification`. Others (`training`, `evals`, `datasets`, `persona_metrics`) stay.

**Considered & rejected:**
- *Lock taxonomy upfront* — locks decisions before we know how the modules compose.
- *Keep all existing names* — `inference` and `editing` are unclear to external readers (user flagged this explicitly).

**Why:** User leaned to "defer taxonomy decisions to per-slice migration"; we keep that flexibility while committing to the two anchor renames where the existing names are most opaque.
